# 中断验证（备份与副本）

`examples/interruptions.py` 是一套独立的、可重跑的中断验证。它不是单元测试套件（项目的自动化测试仍为 deferred），而是用真实生产 API 在临时数据库上制造提交、目录变化、分段接收、重复包和受控的**操作系统进程中断**，然后从全新进程核对恢复后的事实。

运行：

```
python3 -I examples/interruptions.py                 # 自动清理临时目录
python3 -I examples/interruptions.py --keep DIR      # 保留全部数据库与 report.json 证据
```

约 5 秒，不需要联网，只使用标准库。

## 为什么用独立进程观察

方法返回成功或两个 revision 相等，无法区分字节已经落盘与状态仅缓存在仍在运行的进程内。本验证采用三层递进的观察方式：

1. **冷进程重读**：每次“是否持久化”的判断都在一个全新的操作系统进程里打开文件，原写入进程已被 `SIGKILL` 终止，进程内缓存随之消失。
2. **绕过生产读 API 的原始只读读取**：`raw_facts` 用独立的只读 `sqlite3` 连接直接读物理表，核对文档内容、墓碑（`versions.body IS NULL` 的最新版本）、索引投影（`index_defs`/`index_values`）、连续提交日志（`commits` 的 rev 等于 `floor+1..head`）以及各表行数，并对这组事实计算统一的 `fact_digest`。
3. **仅主文件证明**：在无生产句柄持有文件时执行 `wal_checkpoint(TRUNCATE)`，把 WAL 折进主数据库，再把单独的 `.db`（不带 `-wal`/`-shm`）复制到空目录冷读。仅活在 WAL 或进程缓存里的事实在这份副本中会缺失。

中断本身通过对工作进程发送真实 `SIGKILL` 实现；不打补丁、不注入生产模块。备份/恢复的触发点是临时文件出现或按本机校准耗时的比例定时，副本 apply 的触发点是在一次性副本上先校准同包 apply 耗时再按比例定时。

## 覆盖的场景

- **提交持久性**：工作进程提交后未关闭/未刷盘即被杀死；新进程确认修订、文档、幂等回执均已持久化，随后另一个进程在同一段历史上继续写入并成功重放幂等请求。
- **备份中断**：在在线备份的不同耗时比例杀死进程。目标文件要么不存在（发布用的硬链接未执行），要么存在且必然通过完整性与深度检查；从不出现“半成品已发布”。杀死留下的临时文件是惰性残留，同目录重试仍成功。
- **恢复防护与中断**：恢复拷贝阶段被杀死不发布目标；坏校验和、物理截断的损坏归档、已占用目标分别被拒绝，且接收环境逐字节事实不变；占用目标的内容在拒绝前后用 `fact_digest` 证明未被改动。
- **分段副本追赶与中断**：副本基线在源库历史的**中间修订**取得，之后源库继续提交，副本通过分页包追赶。杀死 apply 后从新进程验证整包“全有或全无”（head 只可能停在包前或包后修订），再按重试语义重发直到落地；最终在 head 安装与源库一致的索引投影。
- **重复包**：跨进程重发已应用的包，`applied=0` 且接收环境零变化。
- **坏校验、缺段、错误上游、畸形包、副本主写**：全部整包拒绝，head 与 `fact_digest` 在每次拒绝前后保持不变。
- **目录（catalog）时序**：副本停在 head-1 时收不到当前索引定义；到达 head 的包才安装索引并带入最新 catalog epoch；head 对齐的空提交包幂等且不改变任何文档事实。

恢复为新主库会更换 `database_id` 与 `cursor_secret` 并清理 pin/consumer；恢复为副本保留上游身份并保持 `replica` 模式——两类身份都在断言中显式区分。

## 同一份事实如何对应

源库构建一次后取得 `fact_digest`（覆盖 head/floor、集合模式、当前可见文档、墓碑、索引定义与投影、全部版本行、提交 rev 序列）。恢复出的主库、追赶完成的副本、仅主文件副本都必须得到**同一个 digest**，同时 `PRAGMA integrity_check` 为 `ok`、无外键问题、提交日志连续。运行结束还会再次核对源库 digest 未被验证过程改变。

## 没有覆盖的中断窗口

- `SIGKILL` 无法落在单条 SQLite `IMEDIATE` 事务内部；单提交/单 apply 边界的原子性由 SQLite WAL 保证，验证只在杀死后从新进程证明“全有或全无”的结果，不做事务内指令级故障注入。
- 没有合成最终 `os.link` 发布瞬间的崩溃：POSIX 下该链接本身是原子的；验证覆盖了它之前的临时文件拷贝窗口，并对每个已发布目标做事后校验。
- 不模拟断电、撕裂写、磁盘写满（ENOSPC）、fsync 失败；这些依赖 `synchronous=FULL` 与 SQLite 自身崩溃恢复，硬杀重开只能部分体现。
- 不中断只读的 inspect/校验读取、被动 checkpoint 或变更流读取——它们不修改已提交事实。
- 不涉及网络传输的身份认证；副本包按可信通道数据处理，校验和只检测传输损坏。
