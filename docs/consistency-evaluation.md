# StrataLeaf 一致性技术评估：固定修订读 ≠ 可串行化事务

## 结论先行

同事把"固定修订读取"当成完整可串行化事务是**错误的**。这套库实际提供的隔离能力可以精确概括为：

- **单次读**：多版本快照读，固定修订号可重复读（repeatable read 级别的*单语句*快照）；
- **写批次**：在单个 SQLite `BEGIN IMMEDIATE` 边界内原子提交，带**单文档版本前置条件（CAS）**和**提交期唯一索引检查**；
- **但读和写不共享事务边界**：没有任何 API 能把一次（或一组）读与后续写包进同一个事务。因此库只保证**单键读改写（read-modify-write）的原子性**，不防止**写偏差**和**范围幻读**。

证据脚本在 `/tmp/strataleaf-eval/eval_interleavings.py`，完整 JSON 输出在同目录 `results.json`，全部通过真实生产 API、用两个独立连接句柄 + 事件屏障强制确定性交错得到。

## 1. 四种操作各自到底保证什么

### 1.1 简单 batch（`WriteBatch.commit`）

代码事实（`transaction.py:56-98` + `storage.py:58-71`）：整个批次在一个 `BEGIN IMMEDIATE` 事务里，先循环做完全部前置检查（collection 存在、`expected` 版本、schema 校验），再统一写 `versions`/索引/`commits`，最后推进 `head`。任何一步失败整批回滚。

实验 exp5 证实：

| 场景 | 实际结果 |
|---|---|
| 跨两个集合 2 个操作 | 共享**一个修订号** rev2，`count=2`，一起可见 |
| 批次中一个 `expected=999` 失败 | 整批回滚，head 不动，同批的 `c1/c` 物理上不存在 |
| 同键在一批里出现两次 | 开批时直接拒绝：`one operation per document per batch` |

**保证**：批次内多文档、多集合、索引投影、变更日志的**原子性**（all-or-nothing）和一个线性化提交点。
**不保证**：批次无法断言"我没写的键/集合"在我读和我写之间没有变化——原子性只覆盖提交瞬间，不覆盖决策窗口。

### 1.2 单次 get（`Database.get` / `read_record`）

`mvcc.py:43-48`：每次调用开一个独立 `BEGIN` 只读事务，按 `rev <= 指定修订` 取该键最新版本，调用结束事务即关闭。exp7 证实：

- 显式 `revision=r1` 的多次读取永远返回同一值（100），即使 head 已前进——**单语句快照可重复读**；
- 不带 revision 的两次独立 get 落在不同快照（分别看到 head=2、head=3）；
- **没有任何 API 让一个读事务跨多次调用保持打开**。

所以"固定修订读"是一条**只读、单语句、立即结束**的快照，不是一个可以继续做写的事务。它给的是读一致性，不是读写事务的可串行化。

### 1.3 分页 query + 签名游标

`cursors.py` + `query.py`：游标 HMAC 签名，载荷绑定数据库身份、谓词摘要、**读修订号**、键边界。exp4 证实：

- 第 1 页在 rev5，期间 head 涨到 rev8，第 2 页仍严格在 rev5 快照上（`page2_revision == 5`），不会混入新行——**跨页快照稳定，无不可重复读**；
- 换谓词再用旧游标 → `InvalidCursor: cursor does not belong to this query/read revision`；
- **但游标不是保留租约**（`storage-semantics.md:9` 明确）。无 pin 时 `compact` 把 floor 推到 8 后，翻下一页直接 `SnapshotTooOld: revision 5 is older than retained floor 8`。

**保证**：在快照未被回收前，整个分页序列对应同一一致性快照。
**不保证**：长读不被回收。要跨长操作必须先 `retention.pin`——exp4 中 pin 住 rev1 后 compact 被压回 floor=1（`blocked: true`），旧读继续可用。

### 1.4 带 expected 的读后写（CAS）

`transaction.py:76-79`：提交期在写锁内重读该键当前版本，`expected != current` 即 `Conflict`。这是库唯一的乐观并发控制，且粒度是**单个 (collection, key)**。

**能防丢失更新（单键）**——exp1 双句柄实测：

| 模式 | 两个增量 (+50, +10) 的最终余额 |
|---|---|
| 盲写（不带 expected） | **110**，+50 被静默覆盖，丢失更新发生 |
| 双方都带 `expected=读到的版本` | **150**，后写者收到 `revision conflict ... expected 4, found 5`，必须重读重试 |

`patch()`（`patch.py:19-29`）内部就是"读当前值→合并→以 `expected=current.revision` 提交"，同样只保护这一个键。

## 2. 三类并发异常的防护判定（附实测）

| 异常 | 是否防护 | 实测证据 |
|---|---|---|
| **丢失更新**（同一文档读后写） | ✅ 仅当携带正确 `expected`；盲写不防 | exp1：盲写 100→110 丢更新；CAS 100→150 且冲突报错 |
| **写偏差**（跨集合/跨键的联合决策） | ❌ 不防 | exp2：两个句柄各读两个 roster、各写**不同集合**且都带 expected，两个写**全部成功**，`roster_a/b` 都变成 `on_call=false`，"至少一人值班"不变量被破坏，`conflict_errors=[]` |
| **范围幻读**（基于范围计数/存在性的决策） | ❌ 不防 | exp3：两个句柄都在快照里数到 1 条、容量上限 2，各自 `expected=0` 插入**不同键**，最终 3 条，容量不变量被破坏，无任何冲突 |

**为什么 expected 挡不住后两者**：前置条件只对"本批次实际写入的那个键"做版本比对（`transaction.py:78`）。写偏差中双方写的是不同键，幻读中双方插入的是不同键——没有任何一方的 expected 会命中对方的修改。库没有谓词锁、没有间隙锁、没有可串行化隔离级别（SQLite 默认 `serializable` 只在**单个事务内部**成立，而这里读、写是两个独立事务）。

**唯一索引是唯一的范围级防线，但语义受限**。exp3 同时证实：对 `slot` 建 unique 后，重复 slot 插入在提交期被 `unique index conflict` 拒绝且整批回滚（`b4` 不存在）。也就是说：

- "某字段值全局唯一"这类**等值存在性**约束，可以用唯一索引下沉到提交点，等价于把幻读判定物化；
- 但"容量 ≤ N"（N>1）、"跨集合至少一个为真"这类**计数/跨行/跨集合不变量**，唯一索引无法表达，基线必然漏。
- 另有一个现实限制（README 语义边界）：唯一索引立即约束，交换两个已占用值需先释放，**不支持延迟唯一约束**。

## 3. 两条可落地的演进方向（不改当前实现的前提下评估）

### 方向 A：在应用层用"哨兵文档 + CAS"实现串行化决策（最小侵入，今天就能做）

把跨集合/范围决策收敛到**一个可被 expected 保护的单键**上：

- 写偏差：为每个不变量建一个 `locks/<invariant>` 或计数文档，决策事务以 `expected=该文档当前版本` 对它做一次写（哪怕只是版本推进/计数更新）。两个并发决策中必有一方 CAS 失败重试。
- 容量/幻读：维护 `bookings/counters/<scope>` 计数文档，"插入 + 计数 +1"放进**同一个 batch**，并对计数文档带 expected；不同键的插入因此在同一个键上串行冲突。
- 等值唯一：继续用现有唯一索引，零成本。

**对三个关注点的影响：**

1. **唯一约束**：不依赖新机制，现有 unique index 保留；计数型约束改用哨兵文档表达，吞吐被序列化到热点键（高争用时重试率上升）。
2. **长读保护**：行为不变，仍需调用方显式 `retention.pin`；哨兵方案只解决写冲突，不解决快照回收，分页长读照旧要 pin（exp4 已证明无 pin 会 `SnapshotTooOld`）。
3. **副本日志**：哨兵更新本身就是普通提交，会如实进入 `commits` 并随 `export/apply` 流到副本——**不需要改复制协议**。但要注意 exp6 暴露的两点：(a) 日志记录每一次提交，丢失更新的盲写与合法覆盖在日志里**无法区分**，审计不能只看日志；(b) `compact` 会物理删除 `rev <= floor` 的 commits（exp6 中压缩后 `commits` 表为空、旧 feed 读 `SnapshotTooOld`），所以依赖完整历史的副本/审计必须在 compact 前追赶，或用备份留存。

**代价**：热点键争用、重试逻辑上移到应用、不变量正确性依赖所有写方都遵守约定（绕过哨兵的写入不受保护）。

### 方向 B：在库内引入"谓词/读集前置条件"的真事务能力（改库，投入大）

扩展提交协议，让一个批次可以声明**读集**（读过的修订号集合 + 范围谓词摘要），提交时在 `BEGIN IMMEDIATE` 内校验：自读快照以来，读集中的任何键、或满足谓词的范围是否出现新版本，命中即 `Conflict`。这就是 SSI/乐观串行化的思路。

**对三个关注点的影响：**

1. **唯一约束**：可以把唯一索引检查泛化为"谓词前置条件"的特例，顺带支持**延迟唯一约束**（在提交点统一判定，解决现在"交换唯一值必须先释放"的限制），并能表达容量上限等计数不变量。索引仍需在提交点维护，冲突判定可复用现有 `index_values` 投影。
2. **长读保护**：读集需要一个稳定快照，自然要和 `pins` 机制整合——长事务持有的读修订必须自动注册保留点，否则 `compact` 会让读集校验失去依据。这会把"游标不是租约"的现状改成"事务即租约"，需要新增租约超时/失效语义，否则一个长事务可以无限挡住回收（exp4 已显示 pin 能把 floor 死死压住）。
3. **副本日志**：读集/谓词必须进 `commits` 载荷一起复制，否则副本重放时无法复现冲突判定；但副本只做原子 apply、拒绝主写（exp6 验证 `replica rejects primary writes`，且无 promote API），所以**只需扩展日志格式、不需要在副本上执行冲突检验**。要同步处理 catalog_epoch 与分段追赶语义（当前 `replica.py:47` 在未追到 head 时不装索引），新日志格式要在追赶中段安全降级。

**代价**：读集追踪带来内存与校验成本、谓词重叠判定复杂、需要格式版本升级（当前 `format=1`）和迁移；收益是应用拿到真正的可串行化读写事务，正确性不再靠写方自律。

### 选型建议

- 当前就有跨集合读后写决策、且能接受改造调用方：**先走方向 A**，用哨兵文档 + 现有 CAS 把不变量收敛到单键，零协议变更、复制/备份/回收全部不受影响。
- 若这类不变量会大量出现、或需要库级强制保障（防绕过）：规划**方向 B**，但必须同时设计读集保留租约和日志格式版本，否则长读回收和副本追赶两个现有边界会被打破。

## 4. 可推翻错误直觉的关键实测（汇总）

1. "固定修订读 = 串行化事务" → exp2：双方都基于固定快照做跨集合决策、都带 expected，结果两个写都成功、值班不变量被破坏。读一致性 ≠ 读写可串行化。
2. "带了 expected 就不会丢更新/出幻读" → exp1 证明它只在**同一键**上防丢失更新；exp3 证明不同键的范围插入它完全看不见。
3. "盲写没事，反正是原子提交" → exp1：原子批次照样产生 100→110 的静默丢失更新；exp6：这种覆盖在提交日志里与正常写入无法区分。
4. "签名游标能保护长读" → exp4：游标只固定快照版本，无 pin 时 compact 后翻页直接 `SnapshotTooOld`；真正挡水位的是 `retention.pin`。
5. "唯一索引能兜底所有不变量" → exp3：它能挡等值重复（并整批回滚），但挡不住容量上限这类计数约束。

附：所有实验仅通过公共 API 读取/写入临时数据库，未修改 `strataleaf/` 任何生产文件（`git status` 干净），既有 `compileall` 与 `examples.workflows commit` 均通过。
